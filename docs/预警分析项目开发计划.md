# 物联网传感器预警分析项目开发计划

## 1. 结论

推荐架构：

```text
t_monitor
  -> 新预警分析服务（增量读取、去重、规则状态机、统计聚合）
  -> 预警事件/规则版本/统计结果/通知 Outbox
  -> REST API + SSE
  -> Vue 预警弹窗、仪表盘、后台管理
```

“分析结果落库”是合理的；“前端直接轮询数据库表”不适合作为生产实时方案。前端只能调用后端 API，SSE 用于实时通知，短轮询用于断线补偿和降级。当前规模不需要 Kafka/Flink，Spring Boot 批量消费、内存状态机和 TimescaleDB 聚合足够；达到数万行/秒、多数据源或复杂流计算时再演进。

## 2. 数据基线

只按写入最频繁时段折算，稀疏日期不参与容量平均值。

| 指标 | 结果 |
|---|---:|
| `t_monitor` 行数 | 约 11.58 亿 |
| 可见时间范围 | 约 2026-09-02 至 2026-10-01 |
| TimescaleDB chunk | 20 个，按天分区，全部已压缩 |
| 压缩前/后容量 | 约 153 GiB / 8.5 GiB |
| 全局最忙小时 | 2026-09-28 13:00，9,187,361 行 |
| 最忙小时平均速率 | 约 2,552 行/秒 |
| 最忙分钟 | 2026-09-28 13:56，154,351 行，约 2,573 行/秒 |
| 最忙秒 | 2026-09-28 13:56:26，4,959 行/秒 |

这些数字来自 `t_monitor.time` 的业务采样时间分布，不等于真实事务提交速率。当前表没有 `received_at`、消息 ID 或序列，无法精确识别数据库实际收到批量写入的瞬时速度；上线前应在采集入口补测写入延迟。

生产容量验收建议：

- 规则处理和结果写入按 10,000 行/秒持续、15,000 行/秒突发设计。
- 按 4,959 行/秒峰值进行 30 分钟稳态压测，再做 2 至 3 倍突发压测。
- 模拟重复、乱序、迟到数据，至少覆盖 1% 至 5%。
- 预警按“异常过程”存储，不按超标数据点存储。

## 3. 技术选型

首选：

- Java 17 或 21 + Spring Boot 3.x。
- Maven Wrapper。
- MyBatis + Spring JDBC 批处理；时间序列 SQL 用显式 SQL 控制执行计划。
- Flyway 管理新 schema 的 SQL 迁移。
- PostgreSQL 16 + TimescaleDB。
- Caffeine 缓存传感器和规则配置；多实例需要分布式广播时再加 Redis。
- Micrometer + Prometheus + Grafana。
- Vue 3 + TypeScript + Vite + Pinia + Element Plus + ECharts；如果旧项目是 Vue 2，则沿用 Vue 2，不混用版本。

如果必须和 Java 8 旧系统同机部署，使用 Java 8 + Spring Boot 2.7.18 作为过渡路线，但应把升级 Java 17 纳入计划。新服务对旧业务表使用只读账号，对新 schema 使用独立写账号，Flyway 使用迁移账号。

## 4. 数据模型

建议独立 schema `alert_analytics`。不要让旧表和新表同时成为事实来源。

### 4.1 阈值版本

阈值会反复调试修改，禁止原地覆盖：

```text
alert_rule
  rule_id, rule_code, sensor_no, channel/metric_code, rule_type,
  scope, priority, enabled, current_version_id

alert_rule_version
  rule_version_id, rule_id, version_no, status(DRAFT/PUBLISHED/RETIRED),
  valid_from, valid_to, config_json, created_by, created_at,
  published_by, published_at, change_reason

alert_rule_level
  rule_version_id, level(1/2/3), comparator,
  upper_limit, lower_limit, duration_ms, hysteresis,
  recovery_ms, dedup_ms, notification_level
```

关键约束：

- `(rule_id, version_no)` 唯一。
- 一个版本必须包含三级配置，每级支持持续时间、迟滞、恢复时间和去重窗口。
- 同一规则的有效期不能重叠。
- 发布后的版本不可修改；修改时创建新版本。
- 预警事件保存 `rule_version_id` 和 `threshold_snapshot`，历史告警可以还原当时判定依据。
- 规则缓存带配置版本号，发布后失效并热加载，不重启服务。

调试功能：

- 草稿编辑、参数校验、乐观锁、发布、回滚、停用。
- `POST /rules/{id}/simulate` 对指定历史区间回放，输出命中数量、级别变化、误报/漏报对比。
- `shadow` 模式只计算并记录试运行结果，不发送真实通知。
- 记录修改人、修改前后值、原因、请求 ID、发布时间和审批人。
- 支持批量导入草稿和跨传感器规则集发布，避免多个阈值被分批更新。

### 4.2 预警事件

```text
alert_incident
  incident_id, alert_key, rule_id, rule_version_id,
  sensor_no, channel, alert_type, severity, status,
  first_value, last_value, min_value, max_value,
  started_at, last_seen_at, recovered_at, ack_at, closed_at,
  repeat_count, snapshot_json, revision

alert_event
  event_id, incident_id, event_type, occurred_at, detected_at,
  actor, reason, payload_json

alert_notification_outbox
  outbox_id, incident_id, channel, target,
  status, attempt_no, next_retry_at, error, sent_at
```

状态机：

```text
ACTIVE -> ACKNOWLEDGED -> RECOVERED -> CLOSED
ACTIVE -> RECOVERED
ACTIVE/ACKNOWLEDGED -> CLOSED
```

三级超限是同一异常过程的严重度升级/降级，不是三条独立告警。恢复、确认、关闭和通知发送都写不可变状态流水。开放事件使用部分唯一索引防止同一 `alert_key` 同时出现多个活动事件。

### 4.3 统计和风玫瑰

```text
metric_stat
  bucket_start, bucket_width, sensor_no, channel,
  sample_count, min_value, max_value, avg_value, sum_value,
  first_value, last_value, min_time, max_time,
  late_count, revision_no, is_final

wind_rose_stat
  bucket_start, sensor_no, direction_bin, speed_bin,
  sample_count, calm_count, total_count, speed_sum, speed_max
```

按 1 分钟建立 TimescaleDB continuous aggregate，再生成 5 分钟、小时、日汇总。最大/最小值要保存出现时间。风玫瑰使用 16 个方向桶，风速单独分箱，静风单列；风速和风向按时间容差配对，不能平均角度。

### 4.4 运行状态

```text
sensor_liveness
  sensor_no, channel, last_seen_receive_at,
  offline_due_at, status, state_version, open_incident_id

processing_checkpoint
  stream_name, watermark, last_batch_id, lease_owner,
  last_success_at, last_error
```

## 5. 预警规则

第一阶段规则：

- 离线/心跳超时。
- 三级上下限阈值、持续时间、迟滞、恢复。
- 超物理量程、硬安全边界。
- 传感器死值、物理量程越界与数据写入冲突。
- 停滞/固定值、传感器故障、通信故障。
- 空值、非法值、重复、时间倒退、迟到。
- 滚动 Z-score、MAD/EWMA 等统计异常。
- 系统级数据延迟、计算积压、统计刷新失败。

规则处理：

- 以传感器/指标为 key，在内存中维护滑动窗口和状态。
- 只在 `NORMAL -> LEVEL_1/2/3`、升级、降级、恢复时落库。
- 高限触发 `value >= on_value`，恢复使用迟滞边界；低限反向处理。
- 同时命中三级只保留最高级，但保留证据和变化流水。
- 网关离线时抑制下挂传感器的普通陈旧告警，但保留根因离线事件；硬安全规则不能被维护窗口抑制。

## 6. 1000ms 离线检测

当前数据只有业务时间 `t_monitor.time`，没有真实到达时间。要严格实现“连续 1000ms 无数据”，应在采集入口增加 `received_at` 和 `ingest_id`，离线按 `received_at` 判定，数据异常按 `observed_at` 判定。

当前过渡方案只能：

- 使用 `t_monitor.time` 和水位线近似检测。
- 记录迟到、补传、重复和时间回拨。
- 端到端检测延迟目标 P95 <= 500ms、P99 <= 1s。
- 防抖窗口建议 2 至 3 秒，避免网络抖动造成反复告警。

还有业务冲突：现有传感器频率包含约 `100 Hz`、`1 Hz`、`1/60 Hz`。`1/60 Hz` 传感器约 60 秒一条数据，如果所有传感器统一按 1000ms 判离线，会永久误报。应采用：

```text
offline_timeout_ms = max(1000ms, 2 * expected_interval + jitter)
```

如果 1 秒是强制安全要求，必须为低频传感器配置明确例外并经过业务审批。

## 7. API 与前端

接口前缀 `/api/v1`，新表使用 `timestamptz`；旧的 `timestamp without time zone` 按 `Asia/Shanghai` 解释。

主要接口：

- `GET /sensors`、`GET /sensors/{sensorNo}/channels`
- `GET /stats?sensorNo=&channel=&from=&to=&interval=`
- `GET /wind-rose?sensorNo=&from=&to=`
- `GET /alerts?status=&severity=&sensorNo=&from=&to=&cursor=&limit=`
- `GET /alerts/changes?cursor=`
- `GET /alerts/stream`（SSE）
- `POST /alerts/{id}/ack|resolve|read|suppress`
- `GET /rules`、`POST /rules`、`PUT /rules/{id}`
- `POST /rules/{id}/validate|simulate`

分页使用 `detected_at + event_id` 或不可解释 cursor，不使用大偏移 `OFFSET`。SSE 事件包含 `eventId`、`incidentId`、级别、状态、规则版本和 `Last-Event-ID`，断线后增量补发；REST 短轮询 3 至 5 秒作为兜底。多标签页按事件 ID 去重，避免弹窗风暴。

## 8. 性能目标

| 操作 | P95 | P99 |
|---|---:|---:|
| 单条规则读取/新增/修改 | 150ms | 300ms |
| 预警列表 20 至 50 条 | 250ms | 500ms |
| 预警确认/恢复/关闭 | 250ms | 600ms |
| 7 天、1 分钟统计曲线 | 300ms | 800ms |
| 30 天风玫瑰 | 500ms | 1s |
| 规则计算到事件落库 | 1s | 3s |
| 事件落库到前端可见 | 2s | 5s |

任何页面都不得直接扫描 11.58 亿条 `t_monitor`；历史查询走预聚合和 TimescaleDB 时间桶。`t_monitor(value)` 不建议增加普通 B-tree 索引，阈值判定走流式规则或预聚合。

## 9. 实施里程碑

1. **需求和数据确认**：传感器频率、三级阈值、离线例外、风速/风向映射、保留期、权限矩阵。
2. **数据剖析和兼容**：确认 `t_monitor` 时间语义、重复/空 channel、旧表外键问题、写入入口是否能增加 `received_at`。
3. **项目骨架**：Java/Spring Boot、Flyway、Docker、OpenAPI、健康检查、只读源适配器。
4. **阈值版本和规则引擎**：草稿/发布/回滚、回放试算、三级状态机、去重、迟滞、恢复。
5. **统计分析**：分钟连续聚合、最大/最小值、风玫瑰、迟到数据重算。
6. **通知链路**：Outbox、SSE、增量游标、REST 兜底、已读/确认/关闭。
7. **前端页面**：传感器曲线、最大最小值、风玫瑰、预警弹窗、规则版本管理。
8. **压测和调优**：10,000 行/秒持续、15,000 行/秒突发、重复/迟到数据、CRUD/API P95/P99。
9. **影子运行和灰度**：先只计算不通知，人工比对 7 至 14 天，再按传感器/站点/用户灰度启用通知。

## 10. 主要风险和待确认项

- `1000ms` 离线与 `1/60 Hz` 低频传感器冲突。
- 缺少 `received_at`/`ingest_id`，无法保证严格乱序、迟到和 exactly-once 语义。
- 实际数据约 170 个传感器、308 个传感器通道组合，但配置表约 119 个传感器、199 条通道，存在主数据不一致。
- 约 1,126 万行 `channel=NULL`，另有重复采样行，必须先定义清洗和幂等策略。
- 旧 `t_alert_record` 的外键疑似引用 `id` 而不是 `threshold_id`，迁移时需要修正。
- 业务方必须提供每个传感器的三级阈值，不能只从 `range` 字段自动推导。
- 需要确认旧 Vue/Java 系统是否必须读取 `t_alert_record`、`t_stat_record`；如必须保留，只能作为新事件的兼容投影，不能双写为两个事实来源。
