00结论先行

你的思路是对的，架构方向也是主流。但有三件事必须在动工前定下来，否则做出来会返工。

必须先改 · 需求 1 按字面实现会失效

「连续 1000ms 无数据判离线」不能无差别套用。实测满速时段，占通道数 83% 的 107 个 1 Hz 通道，采样间隔恰好就是 1.000 秒（p99 = max = 1.000 s）。阈值与采样周期相等，余量为零——任何毫秒级抖动都会误判离线。而 12 个 frequency='1/60' 的传感器（挠度仪、靶标）是 60 秒一个点，按 1000ms 判定会永久离线。改法见 02。

必须先查 · 有 13 个通道被两套采集源写进同一个键

QJ-GZ-01 的 x 通道，同一秒里同时存在两条独立物理量序列：一条 50 Hz、量级约 0.5，另一条 1 Hz、量级约 1.8。这是配置错误，不是重复投递。天真的去重会删掉真实的第二个物理量。详见 01 与 11。

需要调整 · 轮询能用，但生态现在的标准是 SSE

「写告警表 → 前端拉取 → 弹窗」这条链路是对的，但若依生态（RuoYi-Vue-Plus）已经把事件型推送默认实现为 SSE，连消息类型枚举里都直接有 alarm。正确的分工是：告警推送走 SSE，看板与统计刷新走轮询。详见 03。

推荐技术栈（一句话）

沿用现有 Spring Boot 体系新建一个独立服务，重活交给 TimescaleDB 的连续聚合（continuous aggregate）和一张心跳读模型表，不要引入 Flink——这个数据量用流处理框架是杀鸡用牛刀，运维成本远超收益。理由见 04。

02需求审查：「1000ms 离线」为什么不能直接用

2.1 三个致命问题

问题 1

阈值等于采样周期，零余量

满速时段实测：107 个 1 Hz 通道的采样间隔 p99 = max = 1.000 秒，0 个通道超过 1.0 秒。阈值和周期相等，网络抖动、采集器调度、时钟对齐的任何一个都会误判。

问题 2

12 个传感器会永久离线

phdm-01~03、phtar-01~06、phtar-J01~03 的 frequency='1/60'，60 秒一个点。按 1000ms 判定，它们从上线第一秒起就永远处于离线告警。

问题 3

真故障会被噪声淹没

实测 2026-09-30 17:30 之后，写入速率从 84,420 行/分断崖式跌到 6,000 行/分（约 60 个通道静默），一直持续到 17:55 数据停止。这是一次真实的采集部分失效——但如果告警表里塞满了抖动误报，没人会注意到它。

2.2 改成两层：数据质量标记 + 离线告警

调研了业界做法后，更准确的改法不是简单放大阈值，而是把「1000ms」从告警触发条件降级为数据质量标记。业界（ThingsBoard、Prometheus、CloudWatch、MQTT 规范）都不用「采样周期倍数」定义离线，而是绝对时间 + 业务容忍度：

系统离线 / 不活跃阈值典型上报周期等效倍数
ThingsBoard600 s3 s200×
Prometheus（序列过期）5 分钟 lookback15~60 s5~20×
CloudWatchN × 评估周期1 分钟起≥ 3×
MQTT Keep Alive（规范建议）检测延迟 1.5×应用相关1.5×

第 1 层：数据质量标记（不告警，只记录）

若 now − last_ts > 1.5 × 采样周期（1 Hz 通道即 > 1.5 秒），写入质量日志/统计表，不产生告警。这正好落在需求原文的 1000ms 附近，既保留了「漏一个采样点」的事实记录，又不制造噪声。

第 2 层：离线告警（满足持续时间才触发）

expected_interval_ms = 1000 / frequency    -- '1'→1000, '1/60'→60000, '10'→100, '50'→20, '100'→10
effective_timeout_ms = max(3 × expected_interval_ms, 10000)   -- 10 秒下限

再加 pending 持续时间（连续 3 次检查都超时才升级为 firing，按 5 秒一轮约 15 秒）和迟滞恢复（连续 3 次检查都有数据才算恢复，不是收到一条就恢复）。

第 3 层：按采集器聚合，抑制风暴

库里的 t_collect_box（6 个）和 t_collect_instrument（12 个）是天然的分组维度。同一采集仪下全部通道都离线时，只发一条「仪器 XXX 离线（影响 N 个通道）」，其余子告警抑制掉；只要还有任一通道上报数据就不判定。这正是 Alertmanager 的 inhibition 模式。

如果一定要严格按需求的 1000ms

那就只把它当作第 1 层的数据质量标记，第 2 层的离线告警仍按上表配置。两者分开，既满足了需求原文，又不会让告警表被噪声淹没。

2.3 离线的判定要加去抖和恢复确认

  • 判定粒度：按通道判定、按传感器聚合上报。一个三向加速度计的 x 通道坏了，不应该报「整个传感器离线」。
  • 确认次数：连续 2~3 个检测周期都判定超时才落库，单次不告警。
  • 恢复确认：连续收到 3 个周期数据才判恢复，避免在临界点反复开关。
  • 冷却期：恢复后 300 秒内同一通道不再触发，压制抖动。
  • 边沿触发：用 LAG() 比较相邻状态，只在「正常 → 异常」的跃变时产生告警。这个模式天然对重复行鲁棒——重复行的状态相同，不会重复触发。考虑到库里已有 1,400~1,700 万行完全重复，这一点很重要。
  • 投运开关：只有 monitor_enabled = true 的通道才参与离线判定（解决 1.3 ⑤ 的 17 个零数据传感器）。
检测精度有上限，这点要提前对齐预期

实测时间戳形如 2026-09-30 17:55:23.9，说明采集器是批量提交的——同一秒内的数据会一起到达。所以离线检测不能基于「两条数据的接收时间差」（应用侧根本看不到接收时间），只能基于库内时间戳做now() − max(time) > threshold，天然是一个定时扫描任务，扫描频率决定检测精度上限。建议 5 秒一轮，即最快 5 秒发现离线。

配套的关键设计：心跳读模型表

离线检测不要每轮去扫 t_monitor（那是 1.37 亿行/天）。维护一张 129 行的 t_sensor_heartbeat，由检测器增量 upsert，离线判定就变成对一张小表的点查——微秒级，完全不碰监控表。这张表同时充当看板实时值的数据源。

03推送方案评估：轮询还是 SSE

你的方案

「这个项目负责写入预警分析数据表，然后前端轮询数据表的数据，如果有新增，就在前端弹窗报警」

结论：这条链路是对的，但「弹窗报警」这一步应该用 SSE，不是轮询。调研改变了我最初的判断，下面是依据。

3.1 先说你的方案哪里是对的

  • 「服务端写表、前端读」这个方向完全正确。告警是服务端产生的状态，前端只是展示方。任何方案都是这个结构。
  • 量级上轮询也撑得住。实测全通道 1 分钟统计只要 47ms；50 个并发用户 5 秒轮询一次 = 10 QPS，数据库毫无压力。按 在线用户数 × 接口数 ÷ 轮询间隔 算，桥梁监测系统的值班人员通常几十人，算出来是几十 QPS 的量级。
  • 看板数据本来就该用轮询。统计卡片、图表这类「快照型」数据用轮询最简单，还能天然配合分页、排序、筛选。

3.2 但「告警弹窗」是事件型推送，生态标准已经变了

调研了若依生态（RuoYi-Vue-Plus，dromara）的源码和官方文档，证据比较硬：

证据内容
官方配置默认值message.transport: sse，注释写明「可选 sse / websocket」。源码 MessageProperties 里 transport 默认值就是 SSE，枚举解析失败时也 orElse(SSE)
官方文档定性5.X 文档：WebSocket「默认关闭（推送建议优先使用 SSE）」「只有确实需要双向通信或长连接自定义协议时再开启」
模块演进5.X 是两套独立模块（ruoyi-common-sse + ruoyi-common-websocket）；6.X 统一成 ruoyi-common-push，抽出 PushSessionManager 接口，SSE 与 WebSocket 两个实现
消息类型PushPayloadDTO.of(type, source, message, data, path) 中 type 的示例值明确包含 alarm，source 包含 device——即若依生态已经把「设备告警推送」当标准用法
原生若依官方 RuoYi-Vue 代码树里根本没有任何推送模块（只有 ruoyi-quartz）。想加推送必须自己集成

所以准确的表述是：若依生态里，「事件型通知」用 SSE（默认）/ WebSocket（可选），「快照型数据」用轮询。你的告警弹窗属于前者。

先确认一件事

现有系统是原生 RuoYi-Vue 还是 RuoYi-Vue-Plus？两者库表结构高度相似（都有 sys_*、qrtz_*、gen_table），从数据库看不出来。如果是 Plus，直接复用 ruoyi-common-push 模块，SSE 推送几乎零成本；如果是原生 RuoYi-Vue，需要自己集成，但也有成熟的社区方案可抄（见 3.5）。

3.3 推荐方案：SSE 推告警 + 轮询刷看板

数据形态例子机制理由
事件型新告警弹窗、告警状态变更、设备上下线SSE 推送发生了才推，天然及时；省掉轮询的无效查询
快照型看板统计卡片、趋势图表、列表分页、历史查询HTTP 轮询数据是「当前状态」不是「事件」；轮询实现最简单，配合分页排序筛选天然

为什么选 SSE 而不是 WebSocket

  • 方向匹配。弹窗只需要服务端推、客户端收，是单向的。WebSocket 的双向能力用不上。
  • 浏览器原生自动重连。SSE 规范里就定义了断线重连（retry 字段控制间隔），不用自己写退避逻辑。WebSocket 的重连、心跳、鉴权全要自己实现。
  • Nginx 配置简单一个量级。SSE 只要 proxy_buffering off 加调大 proxy_read_timeout；WebSocket 要处理 Upgrade / Connection 这两个 hop-by-hop 头（默认不转发），还要靠 ping 帧防 60 秒断连。
  • 若依生态有现成实现。Plus 的 ruoyi-common-push 直接可用。
SSE 的两个已知坑

① HTTP/1.1 下每个浏览器+域名最多 6 条并发连接，多标签页会互相挤占——生产环境上 HTTP/2 就没这个问题（改成协商并发流数，默认 100）。② 浏览器原生 EventSource 不能自定义请求头，所以鉴权 token 只能走 URL 参数。若依官方文档明确说「若前端支持 Header，请优先使用 Header」。

3.4 如果你决定先用轮询（也能接受）

轮询不是错的选择，只是体验差一档。如果先用轮询上线，这四处必须改对：

① 前端轮询后端 API，绝不直连数据库

这一条你大概率已经知道，但值得写下来：数据库永远不暴露给浏览器。

② 用自增游标，不要用时间戳

做法问题
WHERE create_time > $last状态变更（确认、恢复）不会出现在增量里，前端状态永远不刷新
WHERE update_time > $last同一毫秒内多条会漏或重；update_time 是可变列，每次 UPDATE 都改索引，页分裂严重
WHERE seq > $cursor ORDER BY seq推荐。seq 严格单调、只增不减。索引扫描 + Index Cond + LIMIT，无排序节点，代价 O(返回行数)，实测 < 1ms
 
create sequence seq_alert_event;
alter table t_alert_event add column seq bigint not null default nextval('seq_alert_event');
create unique index ux_alert_event_seq on t_alert_event (seq);

select * from t_alert_event where seq > $1 order by seq limit 200;

接口返回 { list, next_cursor, has_more }，前端保存 next_cursor。固定 LIMIT 200 防止一次拉爆。

③ 前端要做去重，否则刷新页面会重复弹窗

浏览器刷新后 cursor 丢了，如果从 0 开始拉就会把历史告警重新弹一遍。把 cursor 存 sessionStorage，同时服务端维护「已确认」状态，前端只对未确认的弹窗。另外注意浏览器会节流后台标签页的定时器（通常降到每分钟一次），用户切走时弹窗会延迟——这正是 SSE 相对轮询的核心优势。

④ 未读数不要每次 count(*)

单独用 Redis 计数器或单行计数表维护，否则每次轮询都要扫一遍活跃告警索引。

5.2 三个关键设计决策

决策一：检测器读「最近窗口」，不读全量

每 5 秒执行一次，只读最近 1~2 分钟的数据（实测约 8.4 万行），实测耗时 42~58ms。全量数据交给连续聚合，检测器永远不碰历史。

决策二：心跳读模型表是离线检测的基础

create table t_sensor_heartbeat (
  sensor_no       varchar(50) not null,
  channel_key     varchar(50) not null default '',   -- coalesce(monitor_code,'')
  last_ts         timestamp   not null,              -- 最后一条数据的 time
  last_value      numeric(15,5),
  expected_interval_ms integer not null,             -- 来自 t_sensor.frequency
  status          smallint    not null default 0,    -- 0未知 1在线 2超时 3离线
  offline_since   timestamp,
  updated_at      timestamp   not null default now(),
  primary key (sensor_no, channel_key)
);

检测器每轮把最近窗口的最新值 upsert 进来，离线判定就变成对这张 129 行表的扫描。

决策三：检测器必须可回放

这一条针对你说的「阈值会反复调试」

把检测逻辑写成以时间窗口为参数的纯函数，而不是绑定 now()。同一个代码路径既能跑实时（窗口 = 最近 1 分钟），也能跑回放（窗口 = 历史某段时间）。

这是必须的：数据止于 2026-09-30，今天已经是 10-18，没有实时数据可测。你调阈值、验证规则、验收功能，全都得靠回放历史。实时模式的「当前时间」应该取 t_monitor 的水位线（max time），而不是墙上时钟——这样回放和实时是同一套逻辑。

07预警规则体系

7.1 标准依据：三级还是四级？阈值取设计值的百分之多少？

这两个问题查了国内外标准和文献，答案可能和预期不一样。

没有任何标准规定「阈值取设计值的百分之多少」

GB 50982-2014 的强制性条文 3.1.8 只写「建筑与桥梁结构监测应设定监测预警值，监测预警值应满足工程设计及被监测对象的控制要求」，条文说明强调「应分级制定」——但正文和附录都不给百分比，也不给等级数。JT/T 1037、T/CECS 529、ISO 系列同样把阈值锚定在「设计值 / 规范容许值 / 长期数据统计基线」上。

如果看到「国标规定黄=60%、红=100%」这类说法，查不到标准出处。那是工程惯例，不是标准条文。

① 最对口的中国标准是 T/CECS 529-2018，而且它是四级不是三级

《大跨度桥梁结构健康监测系统预警阈值标准》（中国工程建设标准化协会，2018-07-16 发布，2018-11-01 施行，主编单位大连理工大学）是目前唯一一部专门规定桥梁 SHM 预警阈值的标准，适用于 300 m 级斜拉桥、500 m 级悬索桥。它采用红 / 橙 / 黄 / 蓝 四级，与中国突发事件应急响应的四级颜色体系一致。

你的需求写的是三级，这没问题——保留三级即可。但建议在字典表里预留 severity = 0（蓝色提示级，只记录不通知），这样将来要扩到四级不用改表结构。实际上本方案的分类体系里已经这么设计了（见 7.2）。

08统计分析与风玫瑰

8.1 定时最大最小值：用连续聚合，不要自己写定时任务

现有 t_stat_record 只有 val_max / val_min 两列，不够用，而且它是空的。建三层连续聚合：

create materialized view cagg_stat_1min
with (timescaledb.continuous) as
select time_bucket('1 minute', time) as bucket,
       sensor_no,
       coalesce(channel,'') as channel_key,
       max(value) as val_max,
       min(value) as val_min,
       avg(value) as val_avg,
       stddev_samp(value) as val_std,
       count(*) as sample_count,
       first(value, time) as val_first,
       last(value, time)  as val_last,
       last(time, value)  as ts_max,       -- 极值发生时间（实测可用）
       first(time, value) as ts_min
from t_monitor
group by bucket, sensor_no, coalesce(channel,'');

select add_continuous_aggregate_policy('cagg_stat_1min',
  start_offset => interval '2 hours',
  end_offset   => interval '1 minute',
  schedule_interval => interval '1 minute');

1 小时和 1 天粒度基于 1 分钟粒度层次化构建（cagg on cagg），避免每次重扫原始数据。

四个必须知道的限制
  • 连续聚合不能 join 外部表，所以「超阈值时长」这类需要对照阈值表的统计做不进去，要另用定时任务写普通表。
  • 改聚合定义要 DROP 重建，重建期间要重新物化全历史（11.58 亿行，预计数十分钟）。上线前务必把统计量定全。
  • 跨粒度汇总均值不能用 avg(val_avg)，必须 sum(val_sum)/sum(sample_count)；标准差同理需要平方和。这是最容易算错的地方。
  • TimescaleDB Toolkit 没装。实测库里只有 plpgsql 和 timescaledb 两个扩展，所以 stats_agg、counter_agg、heartbeat_agg 这些超函数当前用不了。如果要用（对趋势回归、缺失检测很有价值），需要先 CREATE EXTENSION timescaledb_toolkit 并确认服务器有对应的包。不用的话，用原生聚合函数加窗口函数也能实现，只是代码多一些。

8.2 风玫瑰

数据结构已确认：风速和风向是两个 channel，值为 windSpeed / windDirection，时间戳完全对齐（实测 wea-01 每秒恰好 5 行同 timestamp），可以直接按 time 做 pivot，不需要 hash join。

这是有规范依据的功能，不是锦上添花

交通运输部《公路长大桥梁结构监测时空大数据应用指引》（交办公路〔2024〕37 号）强制要求风速风向监测数据「应分析 10min 平均风速、风向，绘制风玫瑰图」。HJ 2.2-2018（环评导则）也要求基本信息底图包含风频玫瑰图，GB 50736-2012 要求给出最多风向及其频率。

三个必须先做的数据处理，顺序不能反

  1. 原始 1 Hz → 10 分钟平均。GB/T 28591-2012《风力等级》和 MOT 指引都用 10 min 平均风速口径。直接拿 1 Hz 原始数据算风玫瑰是错的。
  2. 平均风向必须用矢量法，不能用算术平均——跨 0°/360° 会算错（350° 和 10° 的算术平均是 180°，实际应为 0°）。 
    ux = −Σ(v·sin θ)      uy = −Σ(v·cos θ)      -- 风向是「风的来向」，分量取负号
U  = √(ux² + uy²)
θ  = arccos(ux / U)            当 uy ≥ 0
θ  = 360° − arccos(ux / U)     当 uy < 0

    公式出自 MOT 指引条文说明（原文：「平均风向求解宜采用矢量法」）。负号方向务必用你们仪器的安装朝向和输出定义核实一遍。

  3. 标记静风：10 min 平均风速 ≤ 0.2 m/s 的记录，风向记为静风，不参与方位统计。
纠正一个常见错误：静风阈值是 0.2 m/s，不是 0.5

中国气象局观测体系和 GB/T 35227-2017《地面气象观测规范 风向和风速》表 10.1 明确：静风 C，风速小于或等于 0.2 m/s，且静风不属于任何一个方位。

0.5 m/s 是另一回事——HJ 2.2-2018 第 8.5.2.1 条里的「小风」（风速 ≤ 0.5 m/s 的持续时间）。它和静风是两个概念，原文同一句话里两个阈值并存。网上很多科普文把 0.5 当成静风定义，是把环评的小风判据误读了。

建议：静风阈值用 0.2 m/s（可配置）；同时把「0.5 m/s 以下占比」作为独立指标单列，对齐 HJ 2.2-2018 的小风口径，但不要叫它静风。

设计项取值依据
扇区数16 扇区（每扇 22.5°），可配置 8/36GB/T 35227-2017 与中国气象局观测体系一致，可与气象台站资料直接比对。1 Hz→10 min 聚合后一周只有约 1008 条记录，36 扇区每档仅约 28 条，统计不稳

09性能与容量

9.1 能不能满足「CRUD 一般性能要求」

按单次查询 < 1 秒、列表接口 P95 < 500ms 的口径：

能达标

单通道点查与分页（1~2 ms）、全通道 1 分钟统计（47 ms）、离线检测（42 ms）、1 Hz 通道 24 小时降采样（69 ms）。

不达标

100 Hz 通道的 24 小时原始数据（1.6~2.0 s）、全通道 1 小时聚合（2.4~2.6 s）。根因都是要解压百万行级数据。

对策：这两类查询不要直接打 t_monitor，改走连续聚合。图表接口强制带时间范围并限制返回点数（超过 2000 点就降采样）。所有面向 t_monitor 的查询必须带时间条件——实测无时间过滤的查询规划耗时已达 84.5 ms（20 个 chunk），按 chunk 数线性外推，一年后（365 个 chunk）会到秒级。

12 个 100 Hz 通道贡献了 85% 的行数。两个推论：

  • 扩容要先看它们。如果将来加速度计从 4 个加到 20 个，写入量会翻好几倍。评估新增传感器时，先按「通道数 × 采样率」算一遍行数增量。
  • 模态分析在现有数据形态下做不了。一次模态识别需要 1 小时连续片段（36 万点/通道），扫全量代价极高。真要做模态频率漂移，正确做法是在采集端降采样加特征提取（RMS、峰值、主频、谱峰幅值）后再入库，原始波形只按需回传。这也符合行业惯例——100 Hz 原始波形不应长期全量入库。

9.3 服务器规格

需要扩容的不是分析服务，是数据库

分析服务本身只要 2 vCPU / 4 GB。但当前数据库配置与负载严重错配：shared_buffers 只有 512 MB，而 compress_after = 7 days 意味着常驻约 126 GiB 未压缩数据——缓存与数据量之比是 1:252，近 7 天的查询全是冷读。实测 16 并发时 P95 已经到 602 ms。

11.2 需要你确认的问题

  1. 数据是怎么写进 t_monitor 的？现有后端是通过 MQTT / Kafka 收数再写库，还是采集端直连数据库？这决定了新服务是轮询数据库还是订阅数据流。如果走消息队列，订阅流会比轮询更实时，但要动现有系统。
  2. 现有系统是原生 RuoYi-Vue 还是 RuoYi-Vue-Plus？两者库表结构几乎一样，从数据库分不出来。如果是 Plus，SSE 推送模块是现成的，几乎零成本；如果是原生版，要自己集成。这直接决定第 03 节的方案成本。
  3. 新服务要不要和现有系统共用登录？如果共用，新服务复用同一套 JWT 鉴权和 sys_user 表，前端拿现有 token 直接调；否则要做单点登录。这影响前期工作量。
  4. 现有后端引用了 t_alert_threshold 和 t_stat_record 吗？如果引用了，新表要不要做成兼容视图让老代码零改动？如果没引用（两张表都是空的，很可能只是预留），可以直接替换。
  5. 这 13 个双源写入的通道，第二个源是什么？需要查采集器配置。这是唯一一个「不修就一定会出错」的问题。
  6. 数据库服务器能不能调参和加磁盘？shared_buffers 从 512 MB 提到 8~16 GB 需要改配置并重启。如果这台机器不能动，整个方案的性能预期要下调。
  7. 原始波形要留多久？90 天是一个基于工程经验的建议值。如果有合规或鉴定要求，需要按 3 年规划，磁盘要 1.4 TB。
