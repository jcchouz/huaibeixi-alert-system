# 单通道阈值预警调试指南

本文对应本地“只测试阈值超限，其余预警全部关闭”的调试流程。全部操作只针对
`backend/.env`、`t_monitor` 和测试库，不引入前端或 REST 接口作为生产检测依赖。

## 1. 目标与前提

- 只产生「阈值超限」预警，不产生传感器离线、采集仪离线、传感器死值和超物理量程。
- 只用**一个通道**手工注入样本，数据量小、可重复、便于下断点。
- 统计任务不受影响，仍会按分钟写 `t_stat_record`，这是预期行为。

前提：

1. 使用测试库（当前 `backend/.env` 指向 `huaibeixi_db_test`）。
2. 同一时刻只运行一个会参与检测的后端实例；多实例通过 advisory lock 选主，
   非 leader 实例不会扫描。
3. 不要同时运行 `backend/tools/continuous_simulator.py`，否则同通道会有两份数据。

## 2. 检测链路全景

```text
uvicorn app.main:app
  -> app/api/app.py:create_app()
       app.py:40    AlertAnalyticsEngine(...)                // 进程内唯一检测状态
       app.py:53    alert_type_switches=...                  // 5 个开关
       app.py:76    engine.initialize()
                      -> reload_thresholds()        // 读 t_alert_threshold / t_sensor
                      -> bootstrap_last_seen()      // 初始化各通道 last_ts / online_status
       app.py:83    detection_worker.start()        // 实时预警线程 + 统计线程
  -> app/services/detection.py:136  scan_alerts_once()
       窗口 = [last_scan_at - overlap, now)
       首轮窗口 = [now - max(interval, overlap), now)
  -> app/domain/engine.py:1867      scan_realtime_alerts()
       write_statistics=False, detect_alerts=True, new_samples_only=True
  -> app/domain/engine.py:1353      _run_detection_window()
       engine.py:1397  SAMPLE_BATCH_SQL 读取 t_monitor 原始点
       engine.py:1406  new_samples_only 过滤 time <= 通道 last_ts 的样本
       engine.py:1442  _load_active_alerts() 读取未处理告警
       engine.py:1571  _evaluate_threshold_streak() 逐点累计连续超限
       engine.py:1637  _apply_condition()
       engine.py:1240    is_alert_type_enabled() / active_map 去重
       engine.py:1014    _upsert_alert_incident() 写 t_alert_record
       engine.py:1587  更新 channel_states（下一步扫描继续使用）
```

需要记住的三个设计点：

1. **状态在内存里**：`threshold_streak_count`、`threshold_streak_started_at`、
   `threshold_condition_active` 保存在 `engine.channel_states`，跨扫描轮次累计；
   后端重启后清零，但会通过 `bootstrap_last_seen()` 恢复各通道 `last_ts`。
2. **重复样本不重复计数**：`DETECTION_ALERT_OVERLAP_SECONDS` 让窗口回看，
   `new_samples_only` 只保留严格大于通道 `last_ts` 的样本。
3. **同键同级别不重复写**：`_apply_condition()` 发现该通道已有同类型未处理告警，
   且新级别不更严重时直接返回；只有级别变严重才 `UPDATE` 刷新
   `trigger_count`/`update_time`，不会新增行。

## 4. 快速开始

### 4.1 确认开关

`backend/.env` 中：

```dotenv
DETECTION_ALERT_THRESHOLD_ENABLED=true
DETECTION_ALERT_OFFLINE_ENABLED=false
DETECTION_ALERT_DAQ_OFFLINE_ENABLED=false
DETECTION_ALERT_STUCK_ENABLED=false
DETECTION_ALERT_OOR_ENABLED=false
```

`.env` 只在进程启动时读取，修改后必须重启后端。

### 4.2 停掉旧后端

先关闭标题为 `Huaibeixi-Backend-8090` 的控制台窗口；如果是在 VS Code 终端里
启动的，按两次 `Ctrl+C`。确认端口已释放：

```powershell
Get-NetTCPConnection -LocalPort 8090 -State Listen
```

没有输出表示已停止。如果确实需要按 PID 结束进程：

```powershell
Stop-Process -Id <监听 8090 的 PID> -Force
```

旧实例不停止，新实例会一直等待 advisory lock，表现为 `leader: false`、
`rawPointsProcessed: 0`。

### 4.3 启动后端

直接运行：

```bat
cd backend
run_backend.bat
```

或在 VS Code 运行与调试面板选择 **后端：阈值调试 (8090)**。调试时不要加
`--reload`，避免断点打在子进程上。

检查是否成为 leader、开关是否正确：

```powershell
curl http://127.0.0.1:8090/api/health
```

关注：

```json
  "engine": {
```

### 4.4 注入单通道样本

默认通道是 `stn-01-e/stress`，它当前没有未处理阈值告警，适合反复测试。

```bat
cd backend

```

```powershell
cd backend

```

看到类似输出：

```text

[inject] 目标=level3 upper 注入值=12.25 正常值=0 时长=20s
```

注入器先写一个正常样本（默认值为 0），用于清理后端内存里残留的连续命中状态；
随后每秒写一个超限样本。时间戳取数据库时间，与 Worker 时钟一致。

### 4.5 重复测试

同一通道的未处理告警会阻止新建同级别记录。第二次测试加：

```bat
run_inject_threshold.bat --level 3 --seconds 20 --ack-existing
```

`--ack-existing` 会先把该通道未处理的阈值告警置为已处理，再开始注入。

### 4.6 验证

SQL：

```sql
SELECT seq, sensor_no, channel, alert_type, alert_level, alert_status,
       trigger_val, trigger_count, create_time, update_time
FROM public.t_alert_record
WHERE LOWER(sensor_no) = 'stn-01-e'
  AND COALESCE(channel, '') = 'stress'
  AND alert_type = '阈值超限'
ORDER BY seq DESC
LIMIT 5;
```

API：

```bash
curl -G http://127.0.0.1:8090/api/alerts \
  --data-urlencode "alertType=THRESHOLD" \
  --data-urlencode "alertStatus=0"
```

`THRESHOLD`、`OFFLINE`、`DAQ_OFFLINE`、`STUCK`、`OOR` 是后端支持的英文别名，
会转换成中文预警类型。Windows GBK 控制台直接传中文参数可能被错误编码，
优先使用别名。

同时确认没有其他类型新增：

```sql
SELECT alert_type, COUNT(*)
FROM public.t_alert_record
WHERE create_time > LOCALTIMESTAMP - INTERVAL '10 minutes'
GROUP BY alert_type;
```

## 5. 注入器参数

```text
--sensor       传感器编号，默认 stn-01-e
--channel      通道，默认 stress
--direction    upper 上限超限 / lower 下限超限，默认 upper
--level        1 / 2 / 3，默认 3
--value        显式注入值；指定后不再按 --level 计算
--seconds      注入时长秒数，0 表示一直运行到 Ctrl+C
--interval     采样间隔秒；默认 min(1, 1/frequency)
--ack-existing 开始前处理该通道未处理的阈值告警
--no-reset     不先写正常样本，保留内存中的连续命中状态
--verify-delay 注入结束后等待多久再查询，默认 2 秒
--no-verify    不查询 t_alert_record
--dry-run      只打印计划，不写数据库
```

`stn-01-e/stress` 的阈值和脚本计算值：

| 目标级别 | 阈值上限 | 自动注入值 |
| --- | --- | --- |
| 一级 | 15.0 | 15.3 |
| 二级 | 13.0 | 14.0 |
| 三级 | 11.5 | 12.25 |

查看任意通道的阈值：

```sql
SELECT sensor_no, channel, level1_upper, level2_upper, level3_upper,
       level1_lower, level2_lower, level3_lower, range_min, range_max
FROM public.t_alert_threshold
WHERE LOWER(sensor_no) = 'stn-01-e';
```

如果要测模拟器原生的阈值通道，可以用 `--sensor stn-12-b --channel stress`，
但它在测试库中已有历史未处理告警，需要先加 `--ack-existing`。

### 6.3 推荐 Watch

```text
samples                       # 本轮样本 [(time, value), ...]
rule["confirm_seconds"]       # 3
threshold_count               # 连续命中点数
started_at                    # 本轮连续超限起点
(threshold_snapshot)          # (level, value, limit, fire_time)
threshold_active              # 是否达到连续时长
rule["threshold_condition_active"]  # 上一轮是否已处于命中态
```

调试控制台可以直接查看内存状态：

```python
self.channel_states.get("stn-01-e:stress")
```

### 6.4 按轮次理解运行过程

以 `--interval 1`、`DETECTION_CONFIRM_SECONDS=3` 为例：

| 扫描轮次 | 读到的新样本 | `threshold_count` | `started_at` | `threshold_active` | 动作 |
| --- | --- | --- | --- | --- | --- |
| 第 1 轮 | 正常样本 0 | 0 | None | False | 无 |
| 第 2 轮 | 第 1 个超限样本 | 1 | t1 | False | 无 |
| 第 3 轮 | 第 2 个超限样本 | 2 | t1 | False | 无 |
| 第 4 轮 | 第 3 个超限样本 | 3 | t1 | False | 无（还差时间跨度） |
| 第 5 轮 | 第 4 个超限样本 | 4 | t1 | True | 写告警 |

只要继续超限，后续轮次仍然是 `threshold_active=True`，但
`threshold_condition_active` 已经是 `True`，因此不会重复写新行。
如果读数回到正常，连续状态清零，下一段连续超限会再次触发。

### 6.5 同时调试注入器

需要观察脚本计算值和 SQL 时可以启动 **注入器：单通道阈值样本**。该会话会占用
一个终端；后端调试会话可以同时运行，但注入器结束后不要立即停止后端。

## 7. 常见问题

### 7.1 注入了数据但没有告警

按顺序检查：

1. `/api/health` 的 `detection.leader` 是否为 `true`；不是说明还有旧后端持锁。
2. `.env` 是否在本次进程启动前生效；`engine.alertTypeSwitches` 是否正确。
3. `ENVIRONMENT` 是否为 `test`；`test` 环境不会启动 Worker。
4. 该通道是否已有未处理同级别告警；重复测试加 `--ack-existing`。
5. 样本间隔是否超过 `1.5 / frequency` 秒；超过会重置连续命中。
6. 注入是否发生在后端启动之前；首轮只回看最近 `max(interval, overlap)` 秒。
7. `DETECTION_CONFIRM_SECONDS` 是否仍是 3；如果改大了，注入结束后 2 秒可能
   还没达到确认时长，需要增大 `--verify-delay` 或稍后再查。

### 7.2 为什么只有一条告警

同键同级别不重复写是设计行为，避免每秒扫描都产生新记录。
`tests/test_realtime_detection.py:149` 对此有明确断言。级别升级时会
`UPDATE` 原记录并增加 `trigger_count`，不会新增行。

### 7.3 为什么 `t_stat_record` 还在增长

预警开关只控制预警写入，统计线程独立生成完整窗口记录。关闭其他预警不会停止统计。

### 7.4 为什么第二个后端实例不工作

实时预警和统计各有一把 PostgreSQL advisory lock：

```text
ALERT_ADVISORY_LOCK_KEY      = 0x48425844
STATISTICS_ADVISORY_LOCK_KEY = 0x48425845
```

同一时刻只有一个 leader。调试前必须停掉旧实例。

### 7.5 时间为什么以数据库为准

Worker 使用 `SELECT LOCALTIMESTAMP`，注入器也使用数据库时间，
避免本机与数据库时区/时钟不一致导致样本落在窗口外。

### 7.6 为什么注入器不能用 `with psycopg2.connect(...)`

psycopg2 的连接上下文会保持一个隐式事务，`LOCALTIMESTAMP` 会固定为事务开始
时间。症状是：脚本运行了 10 秒，但所有样本的 `time` 完全相同，阈值连续时长
永远是 0，告警不会产生。

注入器因此使用显式连接并开启 `autocommit=True`，每次写入前重新读取数据库
时间：

```python
conn = psycopg2.connect(DSN)
conn.autocommit = True
try:
    ...
finally:
    conn.close()
```

如果在其他调试脚本里遇到“明明写了很多样本却只算 1 个时间点”，优先检查这一点。

## 8. 清理测试数据

确认只影响测试库后执行：

```sql
-- 查看本次注入的样本
SELECT COUNT(*), MIN(time), MAX(time)
FROM public.t_monitor
WHERE LOWER(sensor_no) = 'stn-01-e'
  AND COALESCE(channel, '') = 'stress'
  AND time >= TIMESTAMP '2026-10-21 00:00:00';

-- 删除注入样本
DELETE FROM public.t_monitor
WHERE LOWER(sensor_no) = 'stn-01-e'
  AND COALESCE(channel, '') = 'stress'
  AND time >= TIMESTAMP '2026-10-21 00:00:00';

-- 删除本次测试产生的告警
DELETE FROM public.t_alert_record
WHERE LOWER(sensor_no) = 'stn-01-e'
  AND COALESCE(channel, '') = 'stress'
  AND alert_type = '阈值超限'
  AND create_time >= TIMESTAMP '2026-10-21 00:00:00';
```

生产环境不要执行删除，改用确认/归档流程。
