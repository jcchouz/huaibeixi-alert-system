# 单通道阈值预警代码链路与调试指南

本文按当前代码整理“外部持续写入 `t_monitor`，后端独立检测阈值超限”的完整链路。
目标是先用一个通道熟悉生产检测骨架，再以同一套方法阅读传感器离线、采集仪离线、
传感器死值和超物理量程。

本文重点不是前端或 REST 操作。前端、REST API 和单通道注入器只用于本地开发、
联调和人工测试。生产检测的关键路径只有：

```text
外部系统 -> t_monitor -> AlertDetectionWorker -> AlertAnalyticsEngine
         -> t_alert_record + t_stat_record
```

## 1. 先记住八个结论

1. 一个传感器通道对应 `t_alert_threshold` 中的一条规则，运行时键为
   `lower(sensor_no):channel`。
2. 阈值按一级、二级、三级依次判断。一级最严重，命中一级后不会再看二级和三级。
3. 判断使用严格不等式：上限必须是 `value > levelX_upper`，下限必须是
   `value < levelX_lower`。值刚好等于阈值不算超限。
4. 阈值超限、超物理量程和传感器死值按连续样本点数判定。阈值超限和
   超物理量程的目标点数为
   `max(3, ceil(t_sensor.frequency * DETECTION_CONFIRM_SECONDS))`，
   死值为 `max(3, ceil(t_sensor.frequency * DETECTION_STUCK_SECONDS))`。
   连续条件不再存放在 `t_alert_threshold`。
5. 通道离线只在本轮扫描没有该通道样本时按时间判定，超时至少为 5 个采样周期：
   `max(5, ceil(t_sensor.frequency * DETECTION_OFFLINE_SECONDS)) / frequency`。
   本轮只要存在该通道任一样本，通道即视为在线。
6. 连续命中状态只保存在当前进程，可以跨扫描轮次，但进程重启后重新累计。
7. `DETECTION_INTERVAL_SECONDS` 只决定扫描频率，不决定阈值确认点数。
8. 同一 `sensor_no + channel + alert_type` 且 `end_time IS NULL` 的记录是同一个
   活动事件。持续同级别超限不会每秒新增记录。
9. `alert_status` 表示人工处理状态，`end_time` 表示条件恢复时间，二者不是一回事。
   人工确认告警不代表阈值条件已经恢复。

## 2. 阈值规则的数据来源

### 2.1 `t_alert_threshold`

阈值检测直接使用以下字段：

| 字段 | 作用 |
| --- | --- |
| `id` | 写入 `t_alert_record.threshold_id` |
| `sensor_no` | 传感器编号 |
| `channel` | 通道编号，空字符串表示默认通道 |
| `physical_quantity` | 物理量名称 |
| `level1_upper/lower` | 一级上限/下限，最严重 |
| `level2_upper/lower` | 二级上限/下限 |
| `level3_upper/lower` | 三级上限/下限 |
| `range_min/range_max` | 超物理量程判定范围，不参与阈值等级计算 |

阈值顺序由阈值管理接口校验：

```text
level1_upper >= level2_upper >= level3_upper
level1_lower <= level2_lower <= level3_lower
```

`confirm_points`、`offline_points`、`offline_timeout_ms` 等旧字段已不在当前阈值表
业务模型中。连续条件统一来自 `backend/.env` 和后端配置。

如果 `range_min/range_max` 为空，引擎会尝试从 `t_sensor.range` 解析物理量程。
物理量名称和单位优先取 `t_sensor_channel`，缺失时再从阈值规则、通道名和物理量
名称推导。

### 2.2 传感器元数据

`t_sensor.frequency` 会由 `load_thresholds()` 解析为 `frequency_hz` 和
`sample_interval_ms`。阈值连续命中的断流判断使用：

```text
max_gap_ms = sample_interval_ms * 1.5
```

`frequency` 支持 `100`、`1/60` 等写法。缺失或非法时回退为 `1 Hz`。

### 2.3 运行时规则

`load_thresholds()` 会合并阈值表、传感器、通道、采集仪和站点元数据，生成
`engine.channel_states` 中的运行时字典。阈值相关字段主要包括：

```text
key
sensor_no_lower
channel
frequency_hz
sample_interval_ms
confirm_seconds
threshold_confirm_samples
stuck_seconds
stuck_confirm_samples
oor_confirm_samples
offline_seconds
offline_confirm_periods
offline_timeout_ms
threshold_streak_count
threshold_streak_started_at
threshold_last_level
threshold_last_value
threshold_last_limit
threshold_condition_active
threshold_condition_level
last_ts
last_val
online_status
offline_condition_active
```

规则只在进程启动时加载一次。每个进程从空的连续命中状态开始，不继承其他进程或
上次运行的运行时状态。

## 3. 生产启动链路

代码入口：[app/api/app.py](../backend/app/api/app.py)

```text
uvicorn app.main:app
  -> create_app()
  -> AlertAnalyticsEngine(...)
       confirm_seconds / stuck_seconds / offline_seconds / alert_type_switches
  -> AlertDetectionWorker(engine, settings)
  -> lifespan
       init_db_pool()
       engine.initialize()
         -> load_thresholds()
       detection_worker.initialize()
         -> 以数据库当前时间建立本次运行边界
       detection_worker.start()
         -> alert-realtime-worker
         -> alert-statistics-worker
```

### 3.1 `load_thresholds()`

位置：[app/domain/engine.py](../backend/app/domain/engine.py:361)

执行顺序：

1. 加载 `t_collect_instrument`、`t_collect_box`、`t_station`。
2. 加载 `t_sensor` 和 `t_sensor_channel`。
3. 读取全部 `t_alert_threshold`。
4. 合并采样频率、物理量程、单位和展示信息。
5. 初始化当前进程内各通道的运行时状态。
6. 一次性替换 `channel_states`。

### 3.2 `begin_detection_session()`

位置：[app/domain/engine.py](../backend/app/domain/engine.py:245)

启动时以数据库当前时间作为边界，并重置当前进程的全部通道状态。启动前仍未
结束的预警会在该边界写入 `end_time`，本次运行不会继承旧连续命中或去重状态。

## 4. 规则加载和首次快照

### 4.1 启动加载

检测进程启动时执行一次 `engine.load_thresholds()`，把阈值及传感器元数据加载到
`channel_states`。运行期间不会重新读取 `t_alert_threshold`，修改数据库后需要重启
后端才能使用新规则。

阈值维护 API 只用于本地管理和人工联调，不在生产检测关键路径上。API 更新只持久化
数据库记录，不改变当前进程已加载的规则。

涉及文件：

- [app/api/routers/thresholds.py](../backend/app/api/routers/thresholds.py)
- [app/services/thresholds.py](../backend/app/services/thresholds.py)
- [app/repositories/thresholds.py](../backend/app/repositories/thresholds.py)

### 4.2 首次规则快照

预警第一次创建时，`_upsert_alert_incident()` 把当时的阈值、量程、确认时长和采样
频率写入 `t_alert_record.rule_snapshot`。同一活动预警后续更新不会覆盖该字段。

## 5. 实时扫描窗口

### 5.1 Worker 循环

代码入口：[app/services/detection.py](../backend/app/services/detection.py:185)

```text
_run_alert_loop()
  -> scan_alerts_once(_current_time())
      _current_time() = SELECT LOCALTIMESTAMP
```

实时扫描和统计线程直接运行，不参与多实例选主。

### 5.2 启动边界

`detection_worker.initialize()` 记录数据库当前时间：

```text
detection_started_at = SELECT LOCALTIMESTAMP
alert_cursor          = detection_started_at
statistics_boundary   = 启动后的完整窗口边界
```

不读取任何历史水位，也不追溯启动前数据。

### 5.3 后续扫描

```text
scan_cursor = 当前进程上一轮扫描结束时间
window_start = scan_cursor
window_end   = min(current_time,
                   scan_cursor + DETECTION_INTERVAL_SECONDS)
```

每轮最多处理一个检测周期。单轮耗时超过周期时，`alertBacklogSeconds` 会增长，
说明当前扫描能力已经低于数据写入速度。

## 6. 引擎如何消费一个扫描窗口

调用链：

```text
AlertDetectionWorker.scan_alerts_once()
  -> AlertAnalyticsEngine.scan_realtime_alerts(window_start, window_end)
  -> _scan_realtime_alerts()
  -> SAMPLE_BATCH_SQL
```

位置：[app/domain/engine.py](../backend/app/domain/engine.py)

一个窗口内按以下顺序执行：

1. 用 `SAMPLE_BATCH_SQL` 读取 `[window_start, window_end)` 内的原始样本。
2. 按 `lower(sensor_no):channel` 分组。
3. 不在 `t_alert_threshold` 中的组合直接忽略。
4. 用各通道 `last_ts` 过滤重复样本。
5. 加载或复用活动告警缓存 `active_map`。
6. 遍历所有已配置通道，而不是只遍历本窗口有数据的通道。
7. 对本窗口没有数据的通道执行离线判断。
8. 对本窗口有任一样本的通道直接标记在线，并依次执行阈值、超量程和死值判断。
9. 写入 `t_alert_record`。
10. 数据库事务提交。
11. 将本轮 `pending_state_updates` 发布到内存 `channel_states`。
12. 更新 `_active_alert_cache`。

关键点：告警写入和状态持久化在同一个数据库事务里。事务失败时，内存中的
`last_ts`、连续命中和活动条件都不会推进。

Worker 处理水位 `t_detection_worker_state` 在引擎返回后单独持久化。即使进程在
两者之间退出，overlap 加 `last_ts` 去重也不会重复累计样本。

## 7. 单个样本的阈值判定

### 7.1 级别判定

位置：[app/domain/engine.py](../backend/app/domain/engine.py:1199)

```text
for level in (1, 2, 3):
    if value > levelX_upper:
        return level
    if value < levelX_lower:
        return level
return None
```

含义：

- 一级优先于二级，二级优先于三级。
- 上限和下限使用同一个级别顺序。
- 等于阈值不算命中。
- 当前实现不单独持久化“上限方向/下限方向”，只保留连续计数、起点和最严重级别。
  从上限直接跳到下限且中间没有正常样本时，连续命中不会因为方向变化自动清零。

### 7.2 连续命中

位置：[app/domain/engine.py](../backend/app/domain/engine.py:616)

每个新样本按以下规则处理：

| 条件 | 状态动作 |
| --- | --- |
| 与上一有效样本间隔超过 `sample_interval_ms * 1.5` | 计数清零、起点清空、最严重快照清空 |
| 样本未命中任何级别 | 计数清零、起点清空、最严重快照清空 |
| 样本命中级别 | 计数加一，首次命中时记录起点，更新本段最严重快照 |
| `threshold_streak_count >= threshold_confirm_samples` | 条件成立 |

### 7.3 时间示例

假设：

```text
采样频率 = 1 Hz
DETECTION_CONFIRM_SECONDS = 3
```

| 样本时间 | 值 | 级别 | 连续计数 | 起点 | 条件成立 |
| --- | ---: | ---: | ---: | --- | --- |
| t0 | 0 | 正常 | 0 | 无 | 否 |
| t1 | 12 | 3 | 1 | t1 | 否 |
| t2 | 12.1 | 3 | 2 | t1 | 否 |
| t3 | 12.2 | 3 | 3 | t1 | 是 |
| t4 | 12.3 | 3 | 4 | t1 | 是 |

确认条件是连续点数。扫描线程每秒执行一次只决定后端多久看到这些样本。

如果 t2 的值升级为一级，连续段内“最严重快照”会变成一级，告警记录的一级
触发时间取该快照首次出现的时间。

样本间隔超过约 1.5 个采样周期会中断当前连续段。

## 8. 阈值告警如何写库

位置：[app/domain/engine.py](../backend/app/domain/engine.py:1634)

判定完成后先生成 `state_updates`，再根据状态变化决定是否写库：

```text
threshold_active = 本段连续条件是否已经成立
previous_threshold_active = 上一轮是否已经成立
previous_condition_level = 当前活动事件已经达到过的最严重级别
```

写库条件：

1. 上一轮还不处于活动条件。
2. 上一轮没有记录活动级别。
3. 本轮级别比当前活动级别更严重，例如 3 级升为 1 级。

持续同级别超限不会调用写库方法。

### 8.1 `_apply_condition()`

位置：[app/domain/engine.py](../backend/app/domain/engine.py:1262)

执行顺序：

1. 条件未成立：返回。
2. `DETECTION_ALERT_THRESHOLD_ENABLED=false`：不写该类告警。
3. 内存 `active_map` 中已有同键活动事件，且新级别不更严重：
   不写库，直接返回原事件。
4. 首次命中或级别升级：调用 `_upsert_alert_incident()`。
5. 将新事件放回 `active_map`，并追加到本轮 `triggered_alerts`。

### 8.2 `_upsert_alert_incident()`

位置：[app/domain/engine.py](../backend/app/domain/engine.py:1029)

数据库活动事件键：

```text
LOWER(sensor_no) + channel + alert_type
WHERE end_time IS NULL
```

数据库还有唯一索引
`ux_alert_record_open_identity`，保证同一个键最多只有一条活动事件。

不存在活动事件时插入：

```text
alert_status = 0
end_time = NULL
create_time = fire_time
threshold_id = 当前阈值规则 id
alert_category = 0
```

已存在活动事件时更新：

```text
seq = nextval(seq_alert_record)
alert_level = LEAST(旧级别, 新级别)
trigger_val = 本轮触发值
threshold_id = COALESCE(新阈值 id, 旧阈值 id)
```

当前告警记录没有 `trigger_count` 和 `update_time`。轮询使用 `seq`，
恢复时间使用 `end_time`。

### 8.3 为什么只有一条记录

持续超限时：

- 内存活动缓存命中同键。
- 状态仍是 `threshold_active=True`。
- 级别没有升级。
- 因而不执行新的 `INSERT` 或 `UPDATE`。

这避免了每秒扫描产生一条重复告警。

### 8.4 降级和恢复

同一活动事件内，记录级别只会升级并在恢复前保持最严重级别。例如一级回落到三级，
不会把记录改回三级。

当样本恢复正常，或本轮无样本且静默时长达到离线条件时：

```text
_close_alert_incident()
  UPDATE t_alert_record
  SET end_time = window_end
```

恢复后再次超限会创建新事件，因为旧事件已经不再满足 `end_time IS NULL`。

### 8.5 `alert_status` 与 `end_time`

| 字段 | 含义 | 谁修改 |
| --- | --- | --- |
| `alert_status` | 人工处理状态，`0` 未处理，`1` 已处理 | 告警确认接口 |
| `end_time` | 检测条件恢复时间，`NULL` 表示活动事件 | 检测引擎 |

重点：

- 人工确认告警设置 `alert_status=1`，但不会自动设置 `end_time`。
- 条件仍在持续时，告警可以同时是“已处理”和“活动中”。
- 条件恢复时，即使 `alert_status=0`，引擎也会写 `end_time`。
- `inject_threshold.py --ack-existing` 是测试专用行为，它同时设置处理状态和
  `end_time`，目的是让同一测试通道可以立即重复产生事件。

## 9. 重启和状态边界

### 9.1 通道状态

通道在线状态、`last_ts`、连续命中计数和条件状态只保存在当前进程的
`channel_states`。项目已删除 `t_detection_channel_state`，不再持久化这些状态。

### 9.2 Worker 水位

实时预警和统计窗口水位只保存在当前进程。启动时以数据库当前时间为新边界，不恢复
历史水位。

### 9.3 规则快照

`t_alert_record.rule_snapshot` 保存预警首次创建时使用的规则内容。后续活动预警更新
不会修改该字段。

### 9.4 启动后的完整顺序

```text
load_thresholds
  -> 加载阈值规则和传感器元数据一次

begin_detection_session
  -> 以数据库当前时间建立检测边界
  -> 清空进程内连续命中、条件状态和活动预警缓存

detection_worker.initialize
  -> 初始化实时预警和统计处理水位
```

重启后连续命中状态从零开始，不读取旧水位或旧通道状态。

### 9.5 删除阈值规则时的注意点

运行中的规则被删除后，该通道不再出现在 `channel_states`，后续扫描不会再评估它。
引擎不会自动根据规则删除动作关闭已存在的活动告警；需要同步关闭时应通过受控迁移
或补充运维流程处理。

## 10. 统计链路为什么独立

实时预警线程：

```text
每 DETECTION_INTERVAL_SECONDS 秒扫描原始样本
不等待统计窗口
不写 t_stat_record
```

统计线程：

```text
只处理已经结束的完整窗口
等待 DETECTION_LAG_SECONDS
写 t_stat_record
不执行预警检测
```

两条线程相互独立：关闭某一类预警开关不会停止统计，统计任务变慢也不会停止
实时预警扫描。

## 11. 单通道快速调试

### 11.1 推荐环境配置

本地调试时在 `backend/.env` 中明确设置：

```dotenv
ENVIRONMENT=development
DETECTION_ENABLED=true

DETECTION_INTERVAL_SECONDS=1

DETECTION_CONFIRM_SECONDS=3

DETECTION_ALERT_THRESHOLD_ENABLED=true
```

注意：

- 其他预警关闭后，引擎仍会读取样本和累计状态，只是不写对应告警。
- 不要同时运行 `continuous_simulator.py`，避免同一通道混入两套数据。

### 11.4 注入样本

```powershell
cd backend
.\run_inject_threshold.bat --level 3 --seconds 20
```

等价命令：

```powershell
cd backend
.\.venv\Scripts\python.exe tools\inject_threshold.py --level 3 --seconds 20
```

注入器行为：

1. 从 `t_alert_threshold` 和 `t_sensor` 读取单通道规则与频率。
2. 根据目标级别计算一个能命中当前级别、但不会命中更高级别的值。
3. 检查计算值没有越过物理量程，避免同时制造超物理量程告警。
4. 默认先写一个正常样本，清空后端已有连续命中状态。
5. 按不超过 1 秒的间隔持续写超限样本。
6. 注入器只写 `t_monitor`，不写告警表和统计表。

常用参数：

```text
--sensor        传感器编号，默认 stn-01-e
--channel       通道，默认 stress
--direction     upper / lower
```

## 15. 常见问题

### 15.1 注入了超限样本但没有告警

按顺序检查：

1. `detection.enabled` 和 `detection.running` 是否均为 `true`。
2. `backend/.env` 是否在本次进程启动前生效。
3. `engine.alertTypeSwitches.阈值超限` 是否为 `true`。
4. `t_alert_threshold` 是否存在完全匹配的传感器和通道。
5. 样本时间是否落在 Worker 处理的扫描窗口内。
6. 样本是否严格超过阈值，而不是等于阈值。
7. 连续命中点数是否达到按频率折算的目标点数。
8. 样本间隔是否超过约 `1.5 / frequency` 秒。
9. 是否已有同键 `end_time IS NULL` 活动事件。
10. 外部写入是否晚于样本时间，且 overlap 仍为 0。

### 15.2 为什么持续超限只有一条记录

同键活动事件只保留一条。持续同级别不会重复写库，级别升级只更新原事件。
这是告警事件去重，不是漏报。

### 15.3 为什么 `alert_status=1` 后没有新告警

人工处理只改变 `alert_status`，不会关闭 `end_time IS NULL` 活动事件。只要条件
仍然成立，引擎继续认为同一事件存在。

需要重复调试时使用注入器的 `--ack-existing`，或者先恢复条件让引擎写
`end_time`，再重新制造超限。

### 15.4 为什么条件已经恢复，`alert_status` 仍是 0

检测恢复和处理状态是两条独立生命周期。`end_time` 表示检测恢复，`alert_status`
表示人工是否处理。

### 15.5 为什么 `t_stat_record` 还在增长

预警开关只控制预警写入。统计线程继续按完整窗口生成 `t_stat_record`。

### 15.6 为什么修改阈值后没有立即生效

规则只在后端启动时加载一次，运行期间不会热更新。修改阈值后需要重启后端。已经创建
的预警继续保留首次写入的 `rule_snapshot`，不会被新规则覆盖。

### 15.7 是否可以同时启动多个后端实例

当前版本按单实例部署，不使用多实例选主。不要同时启动多个检测实例，否则同一批
样本可能被重复处理。

### 15.8 重启后是否会恢复连续命中状态

不会。连续命中状态只保存在当前进程，启动时从数据库当前时间重新开始，不读取
旧水位或旧通道状态。

## 16. 清理单通道测试数据

以下操作只允许在测试库执行。建议使用专用测试传感器，不要直接删除真实业务
通道的历史数据。

如果只是重复调阈值，优先使用 `--ack-existing`，不要删除历史表数据。

需要彻底清理专用测试通道时，先停止后端，避免内存状态继续发布：

```sql
-- 1. 查看测试样本
SELECT COUNT(*), MIN(time), MAX(time)
FROM public.t_monitor
WHERE LOWER(sensor_no) = 'your-test-sensor'
  AND COALESCE(channel, '') = 'your-channel'
  AND time >= TIMESTAMP '2026-10-22 00:00:00';

-- 2. 删除测试样本
DELETE FROM public.t_monitor
WHERE LOWER(sensor_no) = 'your-test-sensor'
  AND COALESCE(channel, '') = 'your-channel'
  AND time >= TIMESTAMP '2026-10-22 00:00:00';

-- 3. 删除测试告警
DELETE FROM public.t_alert_record
WHERE LOWER(sensor_no) = 'your-test-sensor'
  AND COALESCE(channel, '') = 'your-channel'
  AND alert_type = '阈值超限'
  AND create_time >= TIMESTAMP '2026-10-22 00:00:00';
```

清理后重新启动后端，再开始下一轮注入。

生产环境不要执行删除，改用确认、归档和受控数据保留流程。

## 17. 下一类预警的阅读顺序

阈值链路掌握后，其他预警继续沿同一骨架阅读：

```text
AlertDetectionWorker.scan_alerts_once()
  -> AlertAnalyticsEngine.scan_realtime_alerts()
  -> _scan_realtime_alerts()
  -> 各场景 _evaluate_* / _apply_offline_if_due()
  -> _apply_condition()
  -> t_alert_record
  -> 当前进程 channel_states
```

建议下一类先读“传感器离线”：

1. 无样本为什么仍要评估。
2. `last_ts` 和 `online_status` 如何跨轮次保存。
3. `DETECTION_OFFLINE_SECONDS` 如何控制离线确认时间。
4. 离线事件为什么只创建一次。
5. 通道恢复后如何关闭 `end_time`。

之后再读传感器死值、超物理量程和采集仪离线聚合。
