# 后端架构说明

本文档说明当前 `backend/` 目录的架构、各文件夹和源代码文件的职责，以及主要功能的实际调用流程。

## 1. 技术栈与总体定位

后端是一个面向桥梁结构健康监测的告警与统计分析 API，核心技术栈为：

- Python 3.11+
- FastAPI：HTTP 接口、依赖注入、请求校验、OpenAPI
- Pydantic / pydantic-settings：请求响应模型和环境配置
- PostgreSQL / TimescaleDB：原始监测数据、分钟统计、告警和阈值
- psycopg2：数据库连接池、事务和手写 SQL
- Alembic：数据库结构迁移
- Prometheus Client：请求指标

当前访问模型是匿名直接访问，没有登录、用户、角色、JWT 或权限校验。

当前不包含风玫瑰、回放和 SSE。前端通过 REST API 每 5 秒轮询告警，告警确认也通过 REST API 提交。

## 2. 分层结构

后端主要分为以下层：

```text
HTTP 请求
  -> FastAPI Router
  -> Depends 依赖装配
  -> Service 业务编排
  -> Repository SQL 持久化
  -> get_db_cursor()
  -> PostgreSQL / TimescaleDB
  -> Domain Engine 补充设备、通道、等级等运行态信息
  -> Pydantic response_model
  -> JSON 响应
```

各层职责如下：

| 层 | 目录 | 职责 |
| --- | --- | --- |
| API 层 | `app/api/` | 路由、参数解析、依赖注入、响应模型绑定 |
| 核心公共层 | `app/core/` | 配置、日志、异常、序列化 |
| 领域层 | `app/domain/` | 告警类型规则、告警检测引擎、去重与富化 |
| 基础设施层 | `app/infrastructure/` | 数据库连接池、事务、请求中间件 |
| 仓储层 | `app/repositories/` | 手写 SQL，封装表访问 |
| Schema 层 | `app/schemas/` | Pydantic 请求和响应契约 |
| 服务层 | `app/services/` | 用例编排、校验、事务边界、领域对象协作 |
| 迁移目录 | `migrations/` | Alembic 数据库迁移 |
| 测试目录 | `tests/` | 单元测试和 API 契约测试 |
| 工具目录 | `tools/` | 模拟器、接口验证、端到端验证 |

## 8. `app/domain/` 领域层

### 8.1 `domain/alert_types.py`

集中定义告警类型、告警方向、告警分类和归一化函数。

主要告警类型：

- 阈值超限
- 传感器离线
- 采集仪离线
- 传感器死值
- 超物理量程

主要分类：

- `0`：数据预警
- `1`：设备预警

主要函数：

| 函数 | 作用 |
| --- | --- |
| `normalize_alert_type()` | 兼容英文别名并转成当前中文告警类型 |
| `alert_category_for_type()` | 根据告警类型推导数据或设备分类 |

### 8.2 `domain/engine.py`

这是后端核心告警与统计引擎，主要职责包括：

1. 使用进程内普通字典保存通道阈值和跨轮次运行状态。
2. 启动时加载传感器、通道、采集仪、站点和阈值元数据。
3. 使用 TimescaleDB SQL 对原始 `t_monitor` 数据做单次窗口聚合。
4. 生成每分钟 `t_stat_record` 极值统计。
5. 按传感器 `frequency` 计算采样周期，检测连续缺失组数。
6. 检测采集仪离线。
7. 检测连续相同读数的传感器死值。
8. 检测连续超物理量程。
9. 检测连续三级阈值超限。
10. 对相同未处理条件进行告警去重和升级。
11. 为数据库告警行补充传感器名、站点、物理量、单位、等级和分类标签。

关键方法：

| 方法 | 作用 |
| --- | --- |
| `initialize()` | 加载阈值和元数据 |
| `load_thresholds()` | 进程启动时加载一次阈值和设备元数据 |
| `enrich_alert_row()` | 告警响应富化 |
| `_upsert_alert_incident()` | 相同未处理告警更新，否则新增告警 |
| `_load_active_alerts()` | 只加载 `alert_status = 0` 的未处理告警参与去重 |
| `scan_realtime_alerts()` | 只读取原始采样点并执行实时预警规则 |
| `record_statistics_window()` | 只聚合完整窗口并批量写入统计记录 |
| `get_status()` | 返回已加载规则、在线通道、离线通道等状态 |

单实例部署下，实时预警只由 `alert-realtime-worker` 线程处理，统计只由
`alert-statistics-worker` 线程处理。两条链路分别访问自己的游标，不需要扫描重入锁或
引擎步骤锁。`threading.Event` 只用于停止和唤醒后台线程；数据库连接池保留锁，
因为 FastAPI 请求线程和两条后台线程仍会并发借用连接。

当前去重语义：

- 相同传感器、通道和告警类型只复用未处理告警。
- 未处理告警再次命中时更新级别、触发值、触发次数和时间。
- 用户已处理的告警不参与去重。
- 已处理告警之后再次满足相同条件时会新增一条未处理告警。

## 9. `app/infrastructure/` 基础设施层

| 文件 | 作用 |
| --- | --- |
| `infrastructure/database.py` | 创建 `psycopg2` 线程安全连接池，提供连接和游标上下文管理器 |
| `infrastructure/middleware.py` | 注入请求 ID，记录请求日志、耗时和 Prometheus 指标 |

`database.py` 的调用方式：

```text
get_db_cursor()
  -> get_db_conn()
  -> init_db_pool()
  -> ThreadedConnectionPool.getconn()
  -> RealDictCursor
  -> yield cursor
  -> commit / rollback
  -> putconn()
```

写操作使用 `get_db_cursor(commit=True)`。发生异常时自动回滚。

`middleware.py` 会：

- 读取或生成 `X-Request-ID`
- 在响应头返回 `X-Request-ID`
- 统计 `http_requests_total`
- 统计 `http_request_duration_seconds`
- 输出请求方法、路径、状态码和耗时日志

## 12. `app/services/` 服务层

| 文件 | 作用 |
| --- | --- |
| `services/common.py` | `pick()` 参数优先级选择，`parse_datetime()` 时间解析 |
| `services/alerts.py` | 告警查询、轮询、创建、确认、批量确认、删除和响应富化 |
| `services/overview.py` | 合并数据库 KPI 和引擎内存状态，生成首页总览 |

| `services/statistics.py` | 统计传感器列表、极值序列和汇总计算 |

服务层负责业务校验和协作，例如：

- 告警确认只接受状态 `1`。
- 非阈值类告警强制为三级。
- 阈值上限必须满足一级上限不低于二级上限、二级上限不低于三级上限。
- 阈值下限顺序相反。
- 阈值修改只持久化数据库，当前进程已加载的检测规则不变。
- 返回告警前统一调用 `engine.enrich_alert_row()`。

## 13. 启动流程

入口为：

```text
uvicorn app.main:app
  -> app.main
  -> create_app()
  -> 创建 AlertAnalyticsEngine
  -> 创建 FastAPI 和 lifespan
  -> 应用启动
  -> init_db_pool()
  -> await asyncio.to_thread(engine.initialize)
  -> load_thresholds()
  -> detection_worker.initialize()
  -> 以数据库当前时间初始化检测边界
  -> 启动 AlertDetectionWorker
  -> 注册 Router、中间件、异常处理和 /metrics
  -> 开始接收请求
```

应用关闭时会停止 `AlertDetectionWorker` 并执行 `close_db_pool()`。

FastAPI 进程内置 `AlertDetectionWorker`，内部使用实时预警线程和统计线程两条
独立链路。实时预警线程按数据库时钟扫描新写入的原始采样点，默认每秒一次，可通过
`DETECTION_INTERVAL_SECONDS` 配置；统计线程只在完整窗口结束后写入
`t_stat_record`，默认同时生成 1 分钟和 10 分钟窗口，可通过
`DETECTION_WINDOW_MINUTES` 配置逗号分隔的多个窗口。
统计线程按“窗口结束时间 + `DETECTION_LAG_SECONDS`”等待下一次处理，不跟随
实时预警线程逐秒轮询。
实时线程固定延后一个检测周期扫描，默认每秒处理
`[current_time - 2s, current_time - 1s)`，给外部采样点留出落库时间。
实时线程每轮最多推进一个检测周期，扫描耗时超过周期时会在健康状态中累积
`alertBacklogSeconds`；该积压值不包含主动保留的一个周期缓冲。出现积压后，
下一轮从上一轮 `window_end` 继续推进，不会跳到数据库当前时间而漏掉中间窗口。
阈值超限和超物理量程使用 `DETECTION_CONFIRM_SECONDS`，传感器死值使用
`DETECTION_STUCK_SECONDS`，按 `t_sensor.frequency` 折算为
连续样本点数（最少 3 点）。通道离线只在本轮扫描没有该通道样本时按时间判定，
超时至少为 5 个采样周期；本轮只要存在任一样本，该通道即视为在线，不检查
采样间隔。采集仪离线复用通道离线结果。服务启动时
不恢复历史水位，实时预警和统计都只处理启动边界之后的数据。阈值超限、
传感器离线、采集仪离线、传感器死值
和超物理量程五类预警分别由 `DETECTION_ALERT_THRESHOLD_ENABLED`、
`DETECTION_ALERT_OFFLINE_ENABLED`、`DETECTION_ALERT_DAQ_OFFLINE_ENABLED`、
`DETECTION_ALERT_STUCK_ENABLED`、`DETECTION_ALERT_OOR_ENABLED` 控制，默认全部
开启；关闭后仅停止写入该类预警，采样与统计继续执行。预警结果写入
`t_alert_record`。本服务按单实例部署，不参与多实例选主。模拟器进程不参与检测。

## 14. 主要调用流程

### 14.1 首页总览

```text
GET /api/overview
  -> overview router
  -> Depends(get_overview_service)
  -> OverviewService.get_overview()
  -> AlertRepository.get_overview_snapshot()
  -> 查询 t_alert_record / t_stat_record
  -> 读取 engine.channel_states 和 engine.sensor_meta
  -> engine.enrich_alert_row()
  -> OverviewResponse
```

### 14.2 告警筛选和分页

```text
GET /api/alerts
  -> alerts router
  -> Depends(get_alert_service)
  -> AlertService.list_alerts()
  -> AlertRepository.list()
  -> 动态 WHERE、COUNT、状态聚合和分页 SQL
  -> engine.enrich_alert_row()
  -> AlertListResponse
```

`statusCounts` 来自后端聚合，表示当前分类和查询范围内的全部、未处理和已处理数量，不使用当前页记录数计算。

### 14.3 告警轮询

```text
前端每 5 秒
  -> GET /api/alerts/poll?afterSeq=N&limit=M
  -> AlertService.poll()
  -> AlertRepository.poll()
  -> SELECT ... WHERE seq > N ORDER BY seq ASC
  -> engine.enrich_alert_row()
  -> items / maxSeq / latestSeq / hasMore
```

### 14.4 告警确认

```text
前端点击处理
  -> POST /api/alerts/{alert_id}/ack
  -> AlertService.acknowledge()
  -> AlertRepository.acknowledge()
  -> UPDATE alert_status = 1
  -> 更新 handle_by = web、handle_time、handle_opinion、update_time
  -> 分配新的 seq
  -> engine.enrich_alert_row()
  -> 返回更新后的告警
```

更新后的告警会获得新的 `seq`，下一次轮询能够同步状态变化。

### 14.5 告警检测与生成

```text
AlertDetectionWorker
  -> 实时预警线程按数据库时钟扫描上一拍至当前时间的新采样
  -> engine.scan_realtime_alerts(window_start, window_end)
  -> _scan_realtime_alerts()
  -> SAMPLE_BATCH_SQL 读取原始采样点
  -> 检测离线、采集仪离线、死值、超量程、阈值
  -> _apply_condition()
  -> _upsert_alert_incident()
  -> INSERT 或 UPDATE t_alert_record

AlertDetectionWorker 统计线程
  -> 按数据库时钟计算最近已结束的平均窗口
  -> engine.record_statistics_window(window_start, window_end)
  -> _record_statistics_window()
  -> WINDOW_AGG_SQL 聚合 t_monitor
  -> UPSERT t_stat_record
```

### 14.6 阈值修改

```text
PUT /api/thresholds/{id}
  -> ThresholdService.update_threshold()
  -> ThresholdRepository.fetch_rule()
  -> 合并旧值和新值
  -> _validate_thresholds()
  -> ThresholdRepository.update_rule()
  -> COMMIT
  -> 返回数据库中的最新规则
```

阈值列表查询直接读取 `engine.channel_states`，不会在每次请求时访问
`t_alert_threshold`。运行中的检测规则只在进程启动时加载一次，修改数据库后需要
重启后端才会影响检测。预警首次创建时会把规则内容写入 `rule_snapshot`。

### 14.7 阈值模拟

```text
POST /api/thresholds/simulate
  -> ThresholdService.simulate()
  -> 从 engine 获取当前规则
  -> ThresholdService._validate_thresholds()
  -> StatisticsRepository.threshold_series_rows()
  -> 逐分钟比较当前阈值和拟调整阈值
  -> 汇总命中等级、告警率和序列点
```

模拟只计算，不修改数据库。

### 14.8 统计极值

```text
GET /api/stats/extremes
  -> StatisticsService.extremes()
  -> StatisticsRepository.resolve_channel()
  -> StatisticsRepository.extremes_rows()
  -> StatisticsRepository.extremes_summary()
  -> 合并引擎中的传感器、单位、阈值和站点信息
  -> ExtremesResponse
```

### 14.9 健康检查

```text
GET /api/health
  -> 返回服务状态和 engine.get_status()

GET /api/ready
  -> 执行 SELECT 1
  -> 成功返回 ready
  -> 数据库异常返回 503
```

## 15. 数据库表关系

后端没有使用 ORM 模型，表结构由迁移和手写 SQL 维护。

| 表 | 作用 |
| --- | --- |
| `t_monitor` | TimescaleDB 原始监测数据，检测窗口从这里聚合 |
| `t_stat_record` | 窗口统计，默认一分钟，保存最大值、最小值、平均值和样本数 |
| `t_alert_record` | 告警记录，保存状态、级别、类型、触发次数和处理人电话等 |
| `t_alert_threshold` | 通道阈值和物理量程 |
| `t_sensor` | 传感器基础信息 |
| `t_sensor_channel` | 通道名称、单位、监测内容和编码 |
| `t_collect_instrument` | 采集仪信息 |
| `t_collect_box` | 采集箱信息 |
| `t_station` | 站点信息 |

主要关系：

```text
传感器 -> 多个监测通道 -> 每个通道一条阈值规则
采集仪 -> 多个传感器
采集箱 -> 多个采集仪
站点 -> 多个采集箱

原始监测数据 -> 平均窗口检测 -> 窗口统计 + 告警记录
```

## 18. `tools/` 工具目录

| 文件 | 作用 |
| --- | --- |
| `continuous_simulator.py` | 持续写入合成监测数据，仅负责生成 `t_monitor` 数据 |
| `api_validation.py` | 对运行中的 API 做接口、CRUD 和契约验证，结束前恢复告警与阈值快照 |
| `e2e_validation.py` | 端到端验证：预检查、造数、检测、断言、清理 |

`continuous_simulator.py` 的主要行为：

- 从 `t_alert_threshold` 和 `t_sensor` 读取通道计划。
- 加速度通道默认按 100 Hz 生成，其他通道默认按 50 Hz 生成。
- 注入阈值超限、死值、超量程、传感器离线和采集仪离线场景。
- 使用数据库本地时间写入 `t_monitor`。
- 不创建检测线程，不写入 `t_stat_record` 或 `t_alert_record`。

## 19. API 兼容和编码约定

- 路由参数同时接受驼峰和下划线命名。
- Service 使用 `pick()` 按明确优先级选择参数。
- 所有数据库行由 `RealDictCursor` 返回字典。
- 数据库值在响应前通过 `serialize_val()` 或 `enrich_alert_row()` 处理。
- 时间统一输出为字符串，避免 FastAPI 直接序列化数据库时间类型时出现格式不一致。
- 数据库写操作统一通过 `get_db_cursor(commit=True)` 控制事务。
- 错误统一使用 `error.code / error.message / error.details`。

## 20. 当前架构边界

当前明确不包含：

- 登录、注册、用户、角色、权限管理
- JWT、Bearer Token、认证依赖
- SSE、WebSocket 或服务端告警推送
- 告警回放接口和回放 Worker
- 风玫瑰接口和页面

告警查询和确认均通过 REST API 完成。前端弹出告警和预警管理页面每 5 秒调用 API 刷新。
